# Оценка русскоязычных рентгенологических отчётов

Реализация процедуры из приложенной статьи **Adaptive Fusion of Clinical, Textual, and Visual Signals for Russian Radiology Report Evaluation under Limited Data**. Подробное сопоставление исходного кода со статьёй и оставшиеся вопросы приведены в [AUDIT_RU.md](AUDIT_RU.md).

Конкретная последовательность после клонирования, объединённое окружение всех английских текстовых метрик и настройки для GPU 40 ГБ описаны в [SERVER_RUNBOOK_RU.md](SERVER_RUNBOOK_RU.md). Новый пример — [configs/train.server40gb.example.json](configs/train.server40gb.example.json), зависимости английской текстовой ветви — `requirements-text.txt`. Проверены прямые ограничения версий по метаданным пакетов; полное разрешение зависимостей и загрузка моделей в этом окружении ещё требуют проверки на сервере.

Обучаются выбор базовых методов, веса их смеси и калибровка. Веса самих Qwen, переводчиков и энкодеров не дообучаются.

Для каждого отчёта вычисляются три признака: русский GREEN, текстовая метрика по переводу RU→EN и согласованность изображения с переведённым кандидатом. Среднее и стандартное отклонение признаков оцениваются только на обучающей части. Качество получается по формуле:

$$S=\operatorname{sigmoid}(a\,(w_{ru}z_{ru}+w_{text}z_{text}+w_{img}z_{img})+b).$$

Веса удовлетворяют ограничениям статьи, а $a>0$ и $b$ минимизируют MSE относительно $1/(1+y)$, где $y$ — число клинически значимых ошибок. Больший результат означает лучшее качество. Отбор конфигурации и оценка качества используют nested CV 5×5; шаг весов по умолчанию 0,05. При равенстве корреляций выбираются меньшая дисперсия внутренней оценки, затем лексикографический ключ; для весов — лексикографический порядок. Seed по умолчанию 42, поскольку статья его не фиксирует.

## Окружения

Контроллер запускает каждый этап как отдельный `conda run -n ENV python pipeline.py worker ...`. Между этапами передаются CSV, модели в памяти между окружениями не передаются. В окружении контроллера не нужны `torch`, `transformers` или `hi-ml-multimodal`.

```bash
conda create -n cxr-fit python=3.11 pip -y
conda run -n cxr-fit python -m pip install -r requirements-fit.txt
```

Отдельно создайте окружения для нейросетевых этапов. Файлы `requirements-qwen.txt`, `requirements-translation.txt`, `requirements-biovilt.txt`, `requirements-radeval.txt` — исходные спецификации для установки, **не проверенные lock-файлы GPU-окружений**. PyTorch и torchvision подбираются под CUDA вашего компьютера и должны быть совместимы друг с другом. Здесь эти зависимости не устанавливались, модели не скачивались.

| Окружение в примере | Этап | Файл зависимостей |
|---|---|---|
| `cxr-qwen` | Qwen3.5-9B, перевод и русский GREEN | `requirements-qwen.txt` |
| `cxr-hy` | HY-MT1.5-7B | `requirements-translation.txt` |
| `cxr-gemma` | TranslateGemma-12B-IT | `requirements-translation.txt` |
| `cxr-radeval` | RadGraph и RadCliQ-v1 | `requirements-radeval.txt` |
| `cxr-ratescore` | RaTEScore | `requirements-radeval.txt` |
| `cxr-biovilt` | CXR-BERT, BioViL-T, изображения | `requirements-biovilt.txt` |

Например, из корня проекта:

```bash
conda create -n cxr-qwen python=3.11 pip -y
conda run -n cxr-qwen python -m pip install -r requirements-qwen.txt
```

Остальные окружения создаются аналогично. Каждый worker импортирует общие функции, поэтому базовые зависимости из `requirements-fit.txt` включены во все спецификации. Для TranslateGemma нужен разрешённый доступ к gated-модели Google; авторизацию Hugging Face настройте до запуска. Токены в JSON не сохраняйте.

Сохраните окончательные зависимости рабочего окружения через `conda env export -n ENV > ENV.lock.yml` и `conda run -n ENV python -m pip freeze > ENV.pip.txt`. Версии установленных пакетов также записываются в метаданные каждого завершённого этапа. Для воспроизводимости используйте неизменяемые локальные snapshot-каталоги весов вместо изменяемого `main` на Hugging Face: поле модели принимает путь к такому каталогу. Визуальная модель фиксирована в коде как `ImageModelType.BIOVIL_T`, её веса загружает `hi-ml-multimodal`; произвольный визуальный checkpoint эта версия не принимает.

## Конфигурация обучения

Возьмите [configs/train.example.json](configs/train.example.json). Пути `input_csv` и `image_root` считаются относительно файла конфигурации; относительные пути изображений в CSV — относительно `image_root`, а при его отсутствии относительно CSV. Укажите реальные пути к снимкам: в репозитории их нет.

CSV должен содержать непустые `candidate`, `reference`, `image`, а для обучения — числовой неотрицательный `target`. Поле `columns` связывает их с вашими названиями. Идентификатор `row_id` должен быть непустым и уникальным; строки с ID `001` и `1` различаются. Если `row_id` не задан и `report_id` отсутствует, создаются последовательные ID.

В `models` задаются пути или идентификаторы моделей, в `runtime` — устройство, GPU, размеры батчей и лимиты генерации. Промпты и небольшой терминологический словарь находятся в исходных модулях; для точного воспроизведения статьи нужно сверить их с экспериментальными версиями.

В `environments` можно указывать имя conda-окружения или массив аргументов, например `["/opt/conda/envs/cxr-qwen/bin/python"]` либо `["conda", "run", "-p", "/path/to/env", "python"]`. Команды запускаются без shell-интерполяции. Приоритет: точный ID этапа → семейство (`translate.qwen`, `text.biovilt`) → общий тип (`translate`, `text`, `image`) → `default`.

Пять настроек перевода образуют 35 текстовых признаков и 5 визуальных. Текстовая и визуальная ветви конфигурации используют один и тот же сохранённый перевод. TranslateGemma имеет только `noterms`. Чтобы сократить эксперимент, можно явно уменьшить `methods` или список переводчиков; тогда пул уже не соответствует полному эксперименту статьи.

**RadCliQ требует отдельного решения.** `training.lower_transform="reciprocal"` буквально следует статье, но код допускает его только для строго положительных значений. Для RadCliQ с нулями или отрицательными значениями используйте [configs/train.signed-radcliq.example.json](configs/train.signed-radcliq.example.json), где явно выбрано `negate`, то есть $-x$. Это сохраняет направление качества на всей вещественной оси, но меняет описанное в статье преобразование; текст статьи и численные результаты потребуется согласовать с этим выбором. Код не заменяет нулевые/отрицательные значения и не меняет преобразование автоматически.

## Вычисление и сохранение признаков

Сначала можно вывести план без загрузки моделей и без доступа к снимкам:

```bash
conda run -n cxr-fit python build_method.py \
  --plan configs/train.example.json --work-dir work/train --dry-run
```

Затем вычислите признаки:

```bash
conda run -n cxr-fit python build_method.py \
  --plan configs/train.example.json --work-dir work/train \
  --features-only --resume
```

Файлы сохраняются постоянно, в том числе при последующем сбое другого этапа:

```text
work/train/base.csv
work/train/translate.qwen.terms.csv
work/train/translate.qwen.noterms.csv
work/train/green.csv
work/train/text.radcliq.qwen.terms.csv
work/train/text.biovilt.qwen.terms.csv
work/train/image.qwen.terms.csv
work/train/features.csv
```

Для каждого этапа рядом сохраняются `*.manifest.json`, `*.versions.json` и описание задания `*.job.json`. CSV содержит `report_id`, необработанные значения метрик, а для GREEN также объяснение и структурированные ошибки. Задания и CSV содержат исходные отчёты; храните их в подходящем для ваших данных месте.

Для запуска одного этапа с его зависимостями:

```bash
conda run -n cxr-fit python pipeline.py run \
  --plan configs/train.example.json --work-dir work/train \
  --only text.radcliq.qwen.terms --resume
```

Доступные ID перечисляет `--dry-run`. Опция `--resume` повторно использует только завершённые результаты с совпадающими настройками, содержимым отчётов, кодом и хешем CSV. Для визуальных этапов при вычислении проверяются также хеши снимков. Изменения целевых меток не требуют пересчёта нейросетевых признаков. Изменения моделей или runtime консервативно инвалидируют кэш всех этапов.

Кэш не проверяет изменения пакетов внутри окружения или обновление удалённых весов под тем же именем. После таких изменений запускайте без `--resume`; для повторяемых экспериментов фиксируйте окружения и snapshots. Один `work-dir` предназначен для одного запуска: параллельно писать в него нельзя.

## Подбор конфигурации и параметров

После вычисления всех признаков:

```bash
conda run -n cxr-fit python build_method.py \
  --plan configs/train.example.json --work-dir work/train \
  --fit-only --output-json quality_method_config.json
```

На этом этапе не загружаются нейросети, не запускаются их окружения и не требуются сами снимки. Проверяются целостность файлов признаков и соответствие плану; хеши исходных снимков берутся из метаданных завершённых этапов. На каждом внешнем фолде выбирается конфигурация по среднему внутреннему $J=-\tau(S,y)$, затем на всей внешней обучающей части заново оцениваются нормализация, веса и калибровка. Внешняя тестовая часть используется один раз. Финальная конфигурация выбирается внутренней CV на всех данных и затем обучается на всех данных.

JSON содержит выбранные признаки, веса, нормализацию, калибровку, модели, параметры генерации, окружения выбранных этапов, результаты внешних фолдов и их отложенные оценки. `objective_J` — положительное качество $-\tau(S,y)$; `kendall_tau_with_errors` — сама корреляция с ошибками. Исторические поля `*_tau` внутри `training` фактически содержат корреляцию с `-y`, то есть $J$.

Пропущенные или бесконечные признаки не заменяются нулями: исправьте соответствующий этап и повторите его. `features.csv` — сводная таблица для анализа, но `fit` собирает данные из проверенных файлов этапов, поэтому ручное редактирование сводной таблицы не меняет обучение.

Чтобы выполнить весь процесс одной командой, уберите `--features-only`/`--fit-only`.

## Инференс

Входной CSV использует названия столбцов из обучающей конфигурации; экспертный target не нужен:

```bash
conda run -n cxr-fit python evaluate.py \
  --config quality_method_config.json \
  --input new_reports.csv --work-dir work/inference \
  --output quality_scores.json --resume
```

Скрипт читает JSON, вычисляет только выбранные компоненты и возвращает `report_id`, `quality_score` в [0,1], значения компонент и объяснение GREEN. Нормализация и калибровка берутся из обучения; на новых данных они не переоцениваются. Параметры генерации также берутся из обученного артефакта.

Для другого компьютера укажите `--execution-config configs/execution.example.json`. Можно менять `device`, `gpu`, `image_root` и пути/имена окружений. Для переноса окружения используйте точные ID выбранных заданий, перечисленные в `extraction_plan.environments` внутри обученного JSON. Названия моделей, промпты и настройки генерации через этот override менять нельзя. Инференс требует ту же версию Python-кода, что и обучение.

Старые JSON версии 1 не содержат калибровки, поэтому требуют повторного подбора параметров. Интерфейс прежних скриптов заменён на `--plan` и постоянный `--work-dir`; `--config` и прежнее длинное имя входного аргумента инференса поддержаны.

## Проверка

```bash
conda run -n cxr-fit python -m unittest discover -s tests -v
```

Тесты проверяют математику, отсутствие утечки при нормализации и калибровке, ограничения весов, состав пула, ID, кэш, обучение и инференс на синтетических признаках. Нейросетевые workers в интеграционных тестах подменены фикстурами. Эти проверки не подтверждают качество моделей и не воспроизводят опубликованную корреляцию 0,6022. Абляции с 15 seeds, статистические тесты и back-translation из экспериментального раздела статьи не реализованы.
